<Info>
  **Resumo:** o caminho assíncrono é o principal: você pede uma **URL assinada**, sobe o arquivo direto no armazenamento e depois **confirma**, o que dispara o pipeline. O resultado chega por [webhook](/api-reference/kyc/eventos-de-webhook) ou por polling. Para até 15 MB existe também o [caminho síncrono](/api-reference/kyc/validacao-sincrona).
</Info>

## Rotas

| Método | Caminho | O que faz |
| --- | --- | --- |
| `POST` | `/registry/{id}/documents/presign` | Gera URL assinada de upload |
| `POST` | `/registry/{id}/documents` | Confirma o upload e dispara o pipeline (`202`) |
| `GET` | `/registry/{id}/documents` | Lista os documentos do cadastro |
| `GET` | `/registry/{id}/documents/{docId}` | Metadados de um documento |
| `GET` | `/registry/{id}/documents/{docId}/result` | Resultado completo, da classificação ao parecer |
| `GET` | `/registry/documents/{docId}/status` | Status/resultado por polling (sem o id do cadastro) |
| `POST` | `/registry/{id}/documents/{docId}/reprocess` | Reprocessa (`202`) |
| `POST` | `/registry/{id}/documents/{docId}/feedback` | Registra a decisão do operador sobre o parecer |
| `GET` | `/registry/{id}/documents/{docId}/integrity` | Confere o selo do parecer armazenado |

## 1. Pedir a URL assinada

`POST /v1/registry/{id}/documents/presign`

```json
{
  "fileName": "contrato-social.pdf",
  "size": 1843200,
  "mimeType": "application/pdf"
}
```

| Campo | Tipo | Nota |
| --- | --- | --- |
| `fileName` | string | Nome do arquivo |
| `size` | inteiro | Bytes. Máximo 52.428.800 (50 MB) |
| `mimeType` | string | `application/pdf`, `image/jpeg` ou `image/png` |

A resposta traz a `url` para o `PUT` e a `key` que identifica o arquivo. Suba o arquivo direto nessa URL, com o mesmo `Content-Type` e o mesmo tamanho declarados.

<Warning>
  A `key` da confirmação é sempre a que o presign devolveu. Não monte a chave no cliente.
</Warning>

## 2. Confirmar e disparar a análise

`POST /v1/registry/{id}/documents` (responde `202`)

```json
{
  "key": "registry/6612a7f30000000000000001/8f2c....pdf",
  "fileName": "contrato-social.pdf",
  "personDocument": "12345678901",
  "expectedType": "CONTRATO_SOCIAL",
  "callbackUrl": "https://api.suaempresa.com/gyra/kyc"
}
```

| Campo | Tipo | Nota |
| --- | --- | --- |
| `key` | string | A chave devolvida pelo presign |
| `fileName` | string | Nome do arquivo |
| `personDocument` | string | Anexa o documento a uma pessoa da árvore societária |
| `callbackUrl` | url | Webhook chamado quando o pipeline terminar |
| `typeHint` | enum | **Afirma** o tipo: o pipeline adota e pula a classificação |
| `expectedType` | enum | **Pede** um tipo: a classificação roda e o resultado é confrontado (`EXPECTED_TYPE_MATCH`) |

A resposta traz o `documentId`. Ver a distinção entre `typeHint` e `expectedType` em [Análise documental](/kyc/analise-documental#tipo-afirmado-x-tipo-pedido).

## 3. Acompanhar

### Por webhook

Assine `registry.document.progress`, `registry.document.assessed` e `registry.document.failed`. Ver [Eventos de webhook](/api-reference/kyc/eventos-de-webhook).

### Por polling

`GET /v1/registry/documents/{docId}/status`

Mesmo corpo da rota de resultado. Use quando não houver webhook configurado.

## 4. Ler o resultado

`GET /v1/registry/{id}/documents/{docId}/result`

```json

  "registryId": "6612a7f30000000000000001",
  "type": "CONTRATO_SOCIAL",
  "expectedType": "CONTRATO_SOCIAL",
  "expectedTypes": [],
  "status": "VALIDATED",
  "version": 2,
  "isCurrent": true,
  "classification": {
    "type": "CONTRATO_SOCIAL",
    "confidence": 0.94,
    "alternatives": [{ "type": "ALTERACAO_CONTRATUAL", "confidence": 0.21 }]
  },
  "ambiguous": false,
  "statusReason": null,
  "stages": {
    "executed": ["CLASSIFY", "EXTRACT", "VALIDATE"],
    "reused": []
  },
  "extraction": { "cnpj": { "value": "12345678000190", "confidence": 0.97, "page": 1 } },
  "fieldConfidences": { "cnpj": 0.97, "companyName": 0.93 },
  "validation": {
    "checks": [
      {
        "code": "EXPECTED_DOCUMENT_MATCH",
        "result": "PASS",
        "message": "CNPJ do documento é o da análise.",
        "evidence": { "page": 1, "excerpt": "CNPJ 12.345.678/0001-90" },
        "source": "DETERMINISTIC"
      }
    ],
    "reconciliation": { "qsaMatched": true }
  },
  "assessment": {
    "verdict": "VALIDO",
    "score": 0.91,
    "justification": "Documento íntegro, titularidade confirmada e registro na Junta conferido.",
    "evidences": [],
    "ruleSetVersion": "org-v7",
    "contentHash": "9f2b...",
    "feedbackVerdict": null,
    "feedbackComment": null,
    "feedbackAt": null,
    "feedbackUserId": null,
    "effectiveVerdict": "VALIDO",
    "decidedByOperator": false
  },
  "processedAt": "2026-09-05T13:07:44.000Z",
  "attempt": 1
}
```

### Campos do envelope

| Campo | O que é |
| --- | --- |
| `type` | O tipo **lido** pela classificação |
| `expectedType` | O tipo que foi **pedido** no envio |
| `expectedTypes` | O **conjunto** pedido, quando o item veio de um requisito societário |
| `status` | Ver [status do documento](/kyc/analise-documental#status-do-documento) |
| `version` / `isCurrent` | Versão do documento e se é a vigente do tipo |
| `classification` | Tipo, confiança e alternativas |
| `ambiguous` | `true` quando outra alternativa passou de 0,35 de confiança |
| `statusReason` | Por que parou num terminal que não é falha técnica |
| `stages.executed` / `stages.reused` | O que rodou nesta tentativa e o que veio reaproveitado |
| `extraction` | Os campos lidos, no [formato daquele tipo](/api-reference/kyc/formatos-de-retorno) |
| `fieldConfidences` | Confiança por campo |
| `validation.checks[]` | As verificações da régua |
| `validation.reconciliation` | Conferência contra a fonte oficial |
| `assessment` | O parecer |

### Cada verificação

| Campo | Valores |
| --- | --- |
| `code` | Código do catálogo (ver [Régua de validação](/kyc/regua-de-validacao)) |
| `result` | `PASS`, `WARN`, `FAIL`, `SKIP` |
| `message` | Frase em português |
| `evidence` | `{ page, excerpt }` ou `null` |
| `details` | Indícios individuais, quando houver |
| `source` | `DETERMINISTIC`, `RECONCILIATION` ou `LLM` |

### O veredito que vale

<Warning>
  Use **`assessment.effectiveVerdict`**, não `assessment.verdict`.

  `verdict` é o parecer da IA, selado pelo `contentHash`, e ele nunca é reescrito. Quando um operador discorda e decide na mão, a decisão entra em `feedbackVerdict` e `effectiveVerdict` passa a ser ela. `decidedByOperator` diz se isso aconteceu.
</Warning>

## Listar documentos

`GET /v1/registry/{id}/documents`

| Query | Nota |
| --- | --- |
| `type` | Filtra por tipo documental |
| `includeHistory` | `true` lista todas as versões; o padrão traz só a vigente por tipo |

## Reprocessar

`POST /v1/registry/{id}/documents/{docId}/reprocess` (responde `202`)

```json
{
  "stages": ["VALIDATE"],
  "forceType": "ALTERACAO_CONTRATUAL",
  "overrideFeedback": false,
  "callbackUrl": "https://api.suaempresa.com/gyra/kyc"
}
```

| Campo | Nota |
| --- | --- |
| `stages` | Subconjunto de `CLASSIFY`, `EXTRACT`, `VALIDATE`. Ausente roda o pipeline inteiro |
| `forceType` | Corrige uma classificação errada. Como afirma o tipo, `EXPECTED_TYPE_MATCH` sai `SKIP` nesta tentativa |
| `overrideFeedback` | Reprocessa por cima de um documento que já tinha decisão humana |
| `callbackUrl` | Webhook do término |

Regras que evitam surpresa:

- Pular `EXTRACT` só funciona quando existe tentativa anterior com extração gravada. Sem ela, a etapa roda.
- Reexecutar `EXTRACT` sempre revalida, mesmo sem `VALIDATE` na lista.
- Não existe `expectedType` aqui: o tipo pedido é atributo do documento, gravado no envio, e viaja em toda tentativa.

Confira `stages.executed` e `stages.reused` no resultado para ver o que rodou de fato.

## Feedback do operador

`POST /v1/registry/{id}/documents/{docId}/feedback`

```json
{
  "verdict": "VALIDO",
  "comment": "Conferido na Junta por telefone; a certidão saiu depois da alteração."
}
```

| Campo | Valores |
| --- | --- |
| `verdict` | `VALIDO`, `INVALIDO`, `INCONCLUSIVO`, `ANALISE_MANUAL` |
| `comment` | Justificativa opcional |

O parecer da IA não é alterado. O resultado passa a expor `feedbackVerdict`, `feedbackComment`, `feedbackAt`, `feedbackUserId`, `effectiveVerdict` e `decidedByOperator`, e dispara `registry.document.decided`.

## Integridade do parecer

`GET /v1/registry/{id}/documents/{docId}/integrity`

Recalcula o hash do conteúdo armazenado e compara com o selo (`contentHash`) gravado na trilha de auditoria. É a resposta auditável para "este parecer é o mesmo que foi emitido na época?".
