<Info>
  **Resumo:** tudo o que liga o seu sistema ao nosso está em **Configurações, API & MCP**: você **gera a credencial de API ali mesmo**, cadastra webhooks e conecta o MCP. Não é mais preciso pedir credencial ao suporte.
</Info>

## Onde fica

Menu lateral, **Configurações**, aba **API & MCP**. A tela mostra, no topo, o endereço da API e o formato da autenticação, e em seguida três seções na ordem em que você precisa delas: **credenciais**, **webhooks** e **MCP**.

<Warning>
  É área de administradores. As credenciais desta tela dão acesso aos dados da organização inteira; compartilhe com cuidado.
</Warning>

## Chaves de API

### Gerar uma credencial

<Steps>
  <Step title="Configurações, API & MCP">
    Na seção **Credenciais de API**, clique em criar.
  </Step>
  <Step title="Dar um nome reconhecível">
    Use algo que você reconheça na hora de revogar: `backend-producao`, `n8n-homologacao`, `esteira-credito`.
  </Step>
  <Step title="Copiar o par">
    A tela mostra o `clientId` e o `clientSecret` e só fecha quando você confirma que copiou.
  </Step>
</Steps>

<Warning>
  O `clientSecret` aparece **uma vez**, na criação, e nunca mais: guardamos apenas o hash dele e não existe rota que o devolva. Ao fechar o painel, o valor é apagado da tela.

  Quem perdeu o segredo cria outra credencial e revoga a antiga, que é a operação certa de qualquer forma: um segredo que alguém precisou reler já esteve em algum lugar que não devia.
</Warning>

### Revogar

A listagem mostra cada credencial com o `clientId` e a data de criação, e cada linha tem a ação de revogar. Revogar apaga a credencial dos dois lados: ela para de autenticar imediatamente.

### Quantas você quiser

Uma por integração e por ambiente é o padrão saudável: dá para revogar a de homologação sem derrubar a produção.

### Quem pode

Quem tem a permissão **gerenciar configurações** (Administrador, Owner, Superuser). O mesmo perfil que cadastra webhook.

### Gerar token

O `clientId` + `clientSecret` são trocados por um **token de acesso com validade de 24 horas**. Seu backend precisa renovar o token antes de expirar.

```bash
curl -X POST https://gyra-core.gyramais.com.br/auth/authenticate \
  -H "gyra-client-id: seu-client-id" \
  -H "gyra-client-secret: seu-client-secret"
```

Resposta:

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expiresIn": 86400
}
```

### Usar

Incluir o token em toda chamada HTTP:

```bash
Authorization: Bearer <token>
```

Exemplo com `curl`:

```bash
curl -X POST https://gyra-core.gyramais.com.br/v2/report \
  -H "Authorization: Bearer <accessToken>" \
  -H "Content-Type: application/json" \
  -d '{
    "document": "43591367000130",
    "policyId": "6612a7f30000000000000001"
  }'
```

## Webhooks

Permitem que a GYRA+ notifique seu backend quando algo relevante acontece (relatório concluído, política avaliada, exportação gerada, decisão manual de analista), em vez de você ficar fazendo polling.

Você configura webhooks **pela tela**, na mesma aba *API & MCP*, ou pela API.

Na tela você escolhe a URL, marca os eventos por categoria, testa o endereço com um disparo real e gira o segredo quando precisar. O catálogo de eventos vem do backend, então evento novo aparece ali sozinho.

<Note>
  Existem duas famílias de eventos, e as duas aparecem na mesma lista:

  - **Relatórios e crédito**, documentada nesta página e em [Criar Webhook](/api-reference/webhook/post-webhook);
  - **Cadastros e solicitações**, com envelope e assinatura próprios, documentada em [Eventos de webhook](/api-reference/kyc/eventos-de-webhook).
</Note>

### Tipos de evento

Cada webhook é registrado para **um único tipo**. Se você quer receber mais de um tipo, registre webhooks separados (mesma URL ou URLs diferentes).

| Tipo | Quando dispara |
| ---- | -------------- |
| `REPORT` | A cada atualização de seção durante o processamento do relatório (granular, muitos disparos por relatório). |
| `REPORT_FINISHED` | Relatório totalmente processado: todas as integrações concluíram e o resultado final está disponível. |
| `REPORT_STATUS` | Analista humano aprovou ou rejeitou manualmente o relatório (via `analyze` ou `re-analyze`). |
| `REPORT_EXPORTED` | Exportação (PDF ou XLS) do relatório foi gerada e está disponível por URL, ou falhou. |
| `CREDIT_POLICY` | Política de crédito foi avaliada e o status mudou (resultado final do motor de regras). |
| `COMMITTEE_FINISHED` | [Comitê de Crédito IA](/concepts/comite-de-credito) concluiu (ou falhou) a deliberação do relatório, tanto na convocação automática quanto na manual. |
| `OPERATION` | Operação (fluxo multi-relatório com cadeia de políticas) concluiu com status final. |

<Warning>
  Os webhooks da organização são copiados para o relatório **na criação dele**. Se você registrar um tipo novo depois, ele não dispara para relatórios que já existiam.
</Warning>

### Configurar

```bash
curl -X POST https://gyra-core.gyramais.com.br/webhook \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "REPORT_FINISHED",
    "url": "https://seu-sistema.com/webhooks/gyra",
    "apiKey": "opcional-chave-enviada-no-header-api-key"
  }'
```

Parâmetros:
- `type` (obrigatório): um dos tipos da tabela acima.
- `url` (obrigatório): endpoint HTTPS que vai receber o `POST`.
- `apiKey` (opcional): se informado, a GYRA+ envia esse valor no header `api-key` de cada requisição, útil para o seu endpoint validar origem.

### Estrutura do payload

Todo webhook entrega um POST com o formato:

```json
{
  "organizationId": "6612a7f30000000000000001",
  "webhookType": "REPORT_FINISHED",
  "data": { ... }
}
```

O conteúdo de `data` varia por tipo:

**`REPORT_FINISHED`**
```json
{
  "content": {
    "reportId": "6612a7f30000000000000001",
    "policyId": "6612a7f30000000000000010",
    "isFinalized": true,
    "finalizedAt": "2026-04-23T14:30:45Z",
    "errors": { "sections": ["PROCESSES"] }
  },
  "compress": false
}
```

**`REPORT`** (seção individual concluída)
```json
{
  "content": { "...dados da seção..." },
  "compress": false
}
```
Os dados da seção concluída vêm em `content`.

**`REPORT_STATUS`** (decisão manual do analista)
```json
{
  "reportId": "6612a7f30000000000000001",
  "analysis": {
    "userId": "user-id-ou-'Política de crédito'",
    "userName": "Nome do analista",
    "status": "REPORT_APPROVED",
    "date": "2026-04-23T14:35:00Z"
  },
  "lastAnalysis": { "..." }
}
```

**`REPORT_EXPORTED`**
```json
{
  "reportId": "6612a7f30000000000000001",
  "exportUrl": "https://...assinado...",
  "exportedAt": "2026-04-23T14:40:00Z"
}
```
Em caso de falha, `exportUrl` vem `null` e o payload inclui `error`.

**`CREDIT_POLICY`**
```json
{
  "content": {
    "reportId": "6612a7f30000000000000001",
    "policyId": "6612a7f30000000000000010",
    "version": 3,
    "status": "APPROVED",
    "risk": "LOW",
    "score": 720,
    "date": "2026-04-23T14:30:45Z"
  }
}
```

**`COMMITTEE_FINISHED`** (deliberação do comitê concluída)
```json
{
  "content": {
    "reportId": "6612a7f30000000000000001",
    "status": "DONE",
    "decision": "APPROVED",
    "synthesis": {
      "decision": "APPROVED",
      "resumo": "Aprovar com ressalvas: caixa e histórico sustentam a operação.",
      "reasoning": "Seis dos sete agentes recomendaram aprovação...",
      "proximaAcao": "Solicitar garantia adicional antes do desembolso.",
      "conditions": ["Garantia adicional de 20% do limite"],
      "confidence": 0.82,
      "alcadaLevel": null
    },
    "deliberationId": "6612a7f30000000000000900",
    "finishedAt": "2026-07-30T14:31:12.004Z"
  }
}
```
O payload é enxuto de propósito: decisão e síntese. Os votos individuais dos agentes e a auditoria ficam em `GET /committee/deliberations/{reportId}`, e a leitura combinada com os pareceres por seção em `GET /report/{id}/insights`. Se a deliberação falhar, `status` vem `ERROR`, `decision` não vem e o payload inclui `error`.

**`OPERATION`**
```json
{
  "operationId": "6612a7f30000000000000100",
  "operationResultId": "6612a7f30000000000000101",
  "document": "43591367000130",
  "status": "APPROVED"
}
```

### Retry

A GYRA+ faz até **3 tentativas** de entrega com backoff exponencial (1s, ~2s, ~5s). Se o seu endpoint retornar `429` com header `Retry-After`, a GYRA+ respeita o tempo antes de tentar de novo. Depois disso, o envio é descartado, planeje idempotência e fallback com polling em `GET /v2/report/:id` para eventuais perdas.

### Boas práticas

- **Responda 2xx rapidamente** e processe o payload de forma assíncrona na sua fila interna.
- **Use `externalId`** no `POST /v2/report` para amarrar o webhook de volta ao seu pedido/cliente.
- **Escolha o tipo certo**: `REPORT_FINISHED` para a maioria dos fluxos (uma entrega por relatório), `REPORT` só se você precisa reagir seção a seção.
- **Fallback com polling** em `GET /v2/report/:id` caso o seu endpoint fique indisponível.

## Conector de IA (MCP)

A terceira seção da tela liga o [MCP da GYRA+](/mcp/o-que-e) ao seu assistente. Ele não usa credencial de API: a autenticação é o seu próprio login da plataforma.

## Restringir acesso via SSO-only

Por padrão, SSO (Google e Microsoft) convive com login por senha. Se você quer **forçar SSO-only** na sua organização, entre em contato com `atendimento@gyramais.com` para habilitar essa configuração.

## Perguntas frequentes

<AccordionGroup>
  <Accordion title="Perdi meu clientSecret, como recupero?">
    Não tem como recuperar: guardamos só o hash. Crie uma credencial nova em *Configurações, API & MCP* e revogue a antiga.
  </Accordion>
  <Accordion title="Posso ter várias credenciais simultâneas?">
    Sim, e é o recomendado: uma por integração e por ambiente (dev, homologação, produção). Você cria quantas precisar pelo painel, sem pedir a ninguém.
  </Accordion>
  <Accordion title="Preciso pedir credencial ao suporte?">
    Não. Desde setembro de 2026 a credencial é gerada por você mesmo em *Configurações, API & MCP*. O suporte segue disponível para dúvidas, mas não é mais o caminho para obter a chave.
  </Accordion>
  <Accordion title="Diferença entre webhook e polling?">
    Webhook é push (GYRA+ te avisa quando o relatório fica pronto). Polling é pull (você consulta `GET /v2/report/:id` até concluir). Webhook é mais eficiente, mas exige endpoint público HTTPS.
  </Accordion>
  <Accordion title="Como testar webhook em dev sem endpoint público?">
    Use ferramentas como [webhook.site](https://webhook.site) para capturar o POST, ou ngrok para expor o seu localhost.
  </Accordion>
</AccordionGroup>
